解决 GLM-5.2 模型 429 (1305 overloaded)

从假限流到真凶（system prompt 内容过滤 + 客户端指纹检测）的完整排查， 给出了不改磁盘、只改请求路径的 Provider-gated 方案。

问题概览

Hermes Agent 使用 zai/glm-5.2 Coding Plan 后疯狂吃 429？

错误代码 429

HTTP 429 状态码，provider code 1305 overloaded 错误

假限流真过滤

Provider-gated 方案

排查过程

从初步排查到关键发现的完整过程

1

初步排查：这不是 Z.ai 的限流

升级了 Z.ai 的 Coding Plan，把 Hermes Agent 的主模型从 DeepSeek V4 Pro 切到 zai/glm-5.2，但第一个请求直接返回 HTTP 429 + provider code 1305。

排查项目：

  • Z.AI 后台显示额度充足（5小时和周额度都在90%以上）
  • 换了一个全新的 Coding Plan key，同样的 429 / code 1305
  • 降低请求长度、砍 tools、换 model 变体，全没用
  • 同一个 key 用 curl 裸调短 prompt，能通
2

缩小变量：同 key 不同 payload

用同一个 key 发两个请求进行对比测试：

成功请求 
curl 裸调:
{"model": "glm-5.2", 
 "messages": [
   {"role":"user",
    "content":"hi"}
 ]}

→ 200 正常返回
失败请求 
Hermes Agent 完整请求:
- system prompt
- tools  
- history

→ 429 / code 1305 
  overloaded
3

关键发现：GitHub #47685

在 GitHub 上找到了情况完全一致的 issue：NousResearch/hermes-agent#47685

复现条件：

  • 同 key、同 endpoint、同 model、同请求长度
  • 唯一变量：system prompt 的具体内容

🔍 关键发现

当 prompt 包含精确短语 "Hermes Agent" 时，返回 429 / code 1305；把它替换成 "Hermes framework"（或任何其他词），立刻 200。

结论：这不是限流，而是 Z.AI Coding Plan 后端对 system prompt 做了内容检测——可能是产品名/客户端指纹检测。

4

再次排查：这个词到底藏在哪

在 ~/.hermes 下搜索 "Hermes Agent"，发现 50 多处命中：

  • SOUL.md ← 身份定义
  • skills/**/SKILL.md ← mandatory guidance + skill 描述
  • agent/system_prompt.py ← 内置 guidance 常量
  • agent/prompt_builder.py ← DEFAULT_AGENT_IDENTITY 等
  • sessions/*.sqlite ← 已持久化的 session system_prompt

⚠️ 为什么不能全库 sed 替换

  • • 污染技能库：SOUL.md、skills 都是积累的内容，一刀切替换会破坏语义
  • • 污染历史 session：已持久化的 session system_prompt 被改后，session resume 时会出现语义漂移
  • • 被版本更新覆盖：Hermes 更新时这些文件被官方版本覆盖，改动静默丢失

解决方案：双层修复

改请求路径，不改磁盘。与其在数据源头逐个替换，不如在最终组装好的字符串上、发送前做一次原地替换。

第一层：System Prompt 内容替换

在 agent/system_prompt.py 的 build_system_prompt() 返回前加一段

# Z.AI Coding Plan 的 glm-5.2 后端会检测 system prompt 里的精确短语
# "Hermes Agent"，命中则返回误导性 429/code 1305。在最终组装好的
# prompt 边界做替换，覆盖所有来源层（SOUL/skills/memory/guidance），
# 不改动磁盘上的文档、技能或历史 session。
provider_lower = str(getattr(agent, "provider", "") or "").lower()
model_lower = str(getattr(agent, "model", "") or "").lower()
if provider_lower == "zai" and "glm-5.2" in model_lower:
    joined = joined.replace("Hermes Agent", "ZCode")

为什么用 provider + model 双重 gate？

  • • provider == "zai"：只有 Z.AI 直连才触发。OpenRouter 转发的 zai-org/glm-5.2 不受影响。
  • • "glm-5.2" in model_lower：只针对触发过滤的模型。glm-5.1 / glm-4.7 如果以后也有类似问题，加进来就行。

为什么放在 build_system_prompt() 尾部？

  • • Prompt caching 是 sacred：一次 session 里 system prompt 字节级稳定，上游 provider 的 KV cache 才能复用。
  • • build_system_prompt() 只在 session 初始化和 context compression 重建时被调用，都是合法的缓存边界。

第二层：客户端指纹 Headers

Z.AI 后端还会看 HTTP headers 判断请求来源

官方客户端带三个指纹头：

User-Agent: ZCode/0.14.8
X-ZCode-App-Version: 0.14.8
X-ZCode-Agent: glm

Header 工厂函数：

def build_zcode_headers() -> dict:
    """Return the ZCode client fingerprint expected by Z.AI Coding Plan."""
    return {
        "User-Agent": "ZCode/0.14.8",
        "X-ZCode-App-Version": "0.14.8",
        "X-ZCode-Agent": "glm",
    }

然后在主 agent 请求路径注入：

elif (
    getattr(self, "provider", None) == "zai"
    or base_url_host_matches(base_url, "api.z.ai")
    or base_url_host_matches(base_url, "open.bigmodel.cn")
):
    self._client_kwargs["default_headers"] = build_zcode_headers()

📋 覆盖范围

Auxiliary 路径（title 生成、context compression、vision 等）也要覆盖，一共四处：pool 解析、credential 解析、async 转换、custom endpoint resolution。每处加同样的 elif 分支。

经验总结

从这次问题排查中学到的经验教训

1

不是所有 429 都是限流

当一个 429 出现在特定 provider + 特定 model + 特定 prompt 内容的组合下，优先考虑内容过滤而不是额度。

2

改请求路径，不改数据

磁盘上的 SOUL.md、skills、session 是用户的资产。运行时的请求是可变流量。全库 sed 替换会把修 bug 变成埋雷。

3

Provider gate 是底线

任何 provider-specific 的 workaround 必须 gated。全局改动会影响不相关的 provider，制造幽灵 bug。

4

Prompt caching invariant 不能破

任何 system prompt 的修改必须在构建边界做，不能在 turn 循环里做。Hermes 的 cache 稳定性是设计核心。

5

客户端指纹检测比你想的常见

从 Kimi（要求 User-Agent: claude-code/0.1.0）到 Z.AI（要求 ZCode headers），越来越多 provider 在网关层做客户端识别。
